📐 Architecture & Concurrency Topology

Fickle is engineered as a zero-copy, highly concurrent WebSocket hub in Go. Each client manages decoupled readPump and writePump goroutines connected via buffered channels with write coalescing and automatic backpressure defense. 

┌─────────────────────────────────────────────────────────────────────────────┐
│                           HORIZONTAL CLUSTER ARCHITECTURE                   │
└─────────────────────────────────────────────────────────────────────────────┘
        Client A                               Client B
           │ (WebSocket)                          │ (WebSocket)
           ▼                                      ▼
    ┌──────────────┐                       ┌──────────────┐
    │ Fickle Node 1│                       │ Fickle Node 2│
    │  (Port 8080) │                       │  (Port 8081) │
    └──────┬───────┘                       └──────┬───────┘
           │                                      │
           │ (Redis Pub/Sub: fickle:broadcast)    │
           └──────────────────┬───────────────────┘
                              ▼
                     ┌──────────────────┐
                     │ Redis Pub/Sub Hub│
                     │  (Message Sync)  │
                     └──────────────────┘

Core Concurrency Model

  • Decoupled Goroutines: Dedicated writePump prevents slow network writes from stalling the event loop.
  • Write Coalescing: If multiple messages are queued in send chan, they are flushed in a single network frame, reducing syscalls under peak load.
  • Thread-Safe Mutex Guards: Atomic session registry and fast read-write mutexes (sync.RWMutex) for room subscriber lookups.
  • Redis Multi-Node Sync: Automatic fanout across cluster instances with origin node filtering to prevent infinite echo loops.
  • Request Tracing: Injects end-to-end trace_id into JSON logs and frame headers for distributed observability.

⚡ WebSocket Frame Protocol

Clients communicate with the server at ws://host:port/ws using structured JSON frames:

Action Direction Required Fields Description
join_room Client → Server action, room Subscribes connection to a specific broadcast channel
leave_room Client → Server action, room Unsubscribes from the specified room
broadcast Client → Server action, data (room optional) Broadcasts message to room members or globally; syncs over Redis
direct_msg Client → Server action, target_id, data Point-to-point delivery to a specific client/session ID
ping Client → Server action Application-level heartbeat request (server returns pong)

  "action": "broadcast",
  "room": "crypto-ticks",

🌐 REST Management Endpoints

GET
/healthz
Health probe returning uptime, active connections, and Redis status.
GET
/api/v1/metrics
Operational telemetry: msgs in/out, active rooms, total sessions.
GET
/api/v1/rooms
List of all active rooms with client membership counts.
POST
/api/v1/broadcast
External webhook endpoint to publish frames into any WebSocket room.

cURL Integration Example

curl -X POST http://localhost:8080/api/v1/broadcast \
  -H "Content-Type: application/json" \
  -H "X-Request-ID: $(uuidgen)" \
  -d '{"room":"crypto-ticks","data":{"symbol":"SOL/USDT","price":198.40}}'
